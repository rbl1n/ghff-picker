# Phase 0 研究：金馬影展個人選片排程與搶票清單

Clarify Round 3 拍板（2026-10-24）：

- **CL-009**：系統端 = 純前端網頁 + 一次性抓資料腳本，無後端。
- **CL-010**：BDD techstack = 網頁與腳本都用 playwright-bdd（TypeScript），同一套 runner。
- **CL-011**：測試策略 = 使用流程走 E2E；排程規則（衝堂、可看、排程目標、搶票順序、備案）以同一套 Gherkin 直接呼叫排程邏輯驗證。

官網勘查（2026-10-24，`https://www.goldenhorse.org.tw/film/programme/schedule/`）：

- 伺服器端渲染 HTML，免登入、免執行 JS；以 `?search_date=YYYY-MM-DD` 切換日期，頁面內含可選日期清單（觀察到 2026-11-06、11-10～11-22）。
- 影城以表頭分組，觀察到「MUVIE」與「台北信義威秀」；TITAN 列在 MUVIE 下，與 CL-004（TITAN = 松仁威秀）一致，故 spec 的「松仁威秀」在資料中對應「MUVIE」。
- 每筆場次有影廳、開演時間、片名（連到 `films/detail/<id>`）、片長、分級；標記以 `title` 屬性表示：影人出席、影片拷貝非英語發音且無英文字幕、非售票之活動場次，另有 spec 未提的「優先特映場」。
- 未驗證：◆（華語無中英字幕）的 `title` 原文、跨午夜場次的呈現方式、11/07～11/09 是否另有場次頁。

## 決策 1：系統端與部署形態

- **Decision**: 靜態單頁網頁（無後端），場次資料以腳本預先抓成 JSON 隨網頁一起部署；部署到免費靜態空間（GitHub Pages 優先，私有 repo 不支援時改 Cloudflare Pages）。
- **Rationale**: spec 只有一個使用者、資料是公開場次快照（CL-008），沒有需要權威狀態的共用資料；今天必須完成（CL-003），省掉伺服器與部署成本。滿足 NFR-004（手機與電腦瀏覽器皆可用）。
- **Alternatives considered**:
  - 前端 + 後端 API：可自動跨裝置同步，也利於下一個兩人 plan，但今天工作量與部署風險明顯增加（CL-009 未採）。
  - 只在本機跑（不部署）：最省事，但手機搶票時打不開（違反 SC-001）。

## 決策 2：場次資料取得

- **Decision**: TypeScript 腳本以 HTTP 逐日抓官網場次頁、用 HTML parser 解析，輸出 `sessions.json`（影片、場次、影廳、影城、標記）；影城取表頭，「MUVIE」對應松仁威秀。快照檔進版控，網頁只讀這份檔案。
- **Rationale**: 官網為伺服器端渲染且有日期參數，解析成本低；快照滿足 CL-008，也讓 E2E 與排程測試有固定資料。FR-001、FR-003、SC-007。
- **Alternatives considered**:
  - 網頁執行時直接抓官網：會被瀏覽器跨網域限制擋下，且受官網可用性影響。
  - 手動複製貼上整理：約 14 天、數百場次，費時易錯。

## 決策 3：前端框架與建置

- **Decision**: Vite + React + TypeScript。
- **Rationale**: 畫面有分層、時段設定、行程、搶票清單與狀態切換，元件化較易維護；生態成熟、實作 subagent 熟悉，降低今天交付風險。
- **Alternatives considered**:
  - 原生 TypeScript 不用框架：依賴最少，但狀態同步到多個畫面要手刻，容易出錯。
  - Svelte / Preact：體積更小，但對今天的時程沒有實質好處。

## 決策 4：排程演算法

- **Decision**: 以影片為單位做精確搜尋（深度優先 + 分支界限）：每部已分層影片選「一個可看場次或不排」，依 spec 排程目標字典序（必看數 → 想看數 → 有空再看數 → ★ 數）比較；以「剩餘影片全排入的樂觀上界」剪枝；同分時以固定順序（影片 id、場次時間）決勝以確保可重現。必看排不下時，對每部未排入必看片判定原因（無可看場次／與哪些必看片衝堂／每日上限）。
- **Rationale**: spec 要求最佳解（FR-008、SC-003）與可重現（NFR-001）；個人片單通常數十部、每片 1～3 場，精確搜尋配剪枝在 10 秒內可完成。
- **Alternatives considered**:
  - 貪婪法（依層級逐一放）：快，但無法保證最佳，違反 SC-003。
  - 整數規劃求解器（如 glpk.js）：保證最佳，但套件大、字典序目標需轉權重，除錯成本高。
- **殘餘風險（未驗證）**: 50 部、多數影片 3 場以上的極端輸入下，搜尋時間未實測；實作時需以 50 部的壓力案例驗證 NFR-001，必要時加入「必看先求可行解」的兩段式搜尋。

## 決策 5：本機保存與跨裝置帶清單

- **Decision**: 使用者狀態（分層、熱門標記、不可看時段、每日上限、手動順序、搶票標記）存在 `localStorage`（FR-022）；跨裝置以「壓縮後放進網址 hash 的分享連結 + QR code」帶到另一台裝置，開啟後匯入該裝置的保存（FR-018）。
- **Rationale**: 不需要後端或帳號；電腦排好後用手機掃 QR 即可（SC-001）。狀態只有使用者偏好，壓縮後網址長度可接受。
- **Alternatives considered**:
  - 匯出 / 匯入 JSON 檔：手機上開檔不順手。
  - 用雲端（Gist、Drive）同步：需要授權與 token，今天做不完。
- **殘餘風險**: 搶票標記若在手機上產生，不會自動回到電腦；本版接受（單人、搶票在手機完成）。

## 決策 6：時間處理

- **Decision**: 所有時間以 Asia/Taipei 牆上時間表示為「日期 + 自當日 00:00 起的分鐘數」，散場可超過 1440 代表跨午夜；不引入時區函式庫。
- **Rationale**: 影展場次全在台北（NFR-005），以分鐘數計算衝堂公式最單純，且自然處理跨午夜邊界。
- **Alternatives considered**:
  - 使用 `Date` 物件 / date-fns-tz：在使用者裝置時區不是台北時容易出錯，且對本需求過重。

## 決策 7：BDD techstack 與測試策略

- **Decision**:
  - 單一 runner：playwright-bdd（TypeScript）跑所有 `.feature`（CL-010）。
  - 使用流程（選片分層、時段設定、行程畫面、搶票清單、標記切換、分享連結）：瀏覽器 E2E，含桌機與手機尺寸兩個 Playwright project（NFR-002、NFR-004）。
  - 排程規則（相容公式、可看判定、排程目標、未排入原因、搶票順序、備案）：同一套 Gherkin，step 直接呼叫排程模組、不開瀏覽器；最佳性以窮舉比對小型資料集驗證（SC-003）（CL-011）。
  - 抓資料腳本：以存下的官網 HTML 樣本驗證解析結果；另以人工抽樣 20 筆比對官網（SC-007）。
- **Rationale**: 一套語言、一套 runner，降低今天的設定成本；規則層直接測讓窮舉驗證又快又準，流程層仍有 E2E 保護。
- **Alternatives considered**:
  - 全部 E2E：最貼近實際，但窮舉最佳性透過瀏覽器過慢。
  - Python behave 測腳本：需維護兩套 runner。
